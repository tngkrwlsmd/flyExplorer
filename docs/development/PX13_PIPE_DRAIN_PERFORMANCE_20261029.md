# PX13/G08 대량 폴더 전송 대기 제거 — 2026-10-29

## 확인한 병목과 수정

실제 supervisor 경로가 helper 직접 호출보다 오래 걸리는 원인을 좁혔다.
`oneAttempt`는 64KiB 이하의 응답 조각을 성공적으로 읽은 뒤에도 helper가
아직 실행 중이면 매번 20ms를 기다렸다. 큰 페이지를 여러 조각으로 받으면
데이터 생산·소비가 진행 중인데도 이 대기가 누적됐다.

읽기 진행이 있으면 바로 다음 반복으로 이동하는 한 조건을 추가했다.
다음 반복의 취소·generation·4.5초 제한·프레임 크기 검사는 유지한다.
데이터가 없을 때만 기존 대기를 사용한다. 체크섬/완전한 응답 검증, helper
종료 후 잔여 데이터 처리, 재시도, Job 소유권, UI/탭 구조와 20k/25k 제한은
변경하지 않았다. 임시 제품 계측이나 새 프로세스 재사용 구조는 추가하지 않았다.

## 동일 조건의 실제 전후 결과

Windows VM, Windows 11 build 26300, x64 Release, 960×519, 96 DPI.
네이티브 측정은 같은 소유 파일 폴더를 전후 재사용했다. 앱 측정은 같은
`benchmark_app_folder.py --items 8000`으로 새 격리 프로필/동일 내용의
파일을 사용했고, 각 실행에서 200개 사전 확인 뒤 8,000개를 검사했다.
추가 키보드/응답성 probe는 켜지 않았다. 한 번씩의 전후 관찰이며 OS 캐시와
호스트 부하는 통제하지 않았다. 전체 환경의 확정적인 개선율로 일반화하지 않는다.

관측된 전체 앱 정렬 감소는 2,550.849ms(약 59.47%), supervisor 8페이지
감소는 약 70.82%다. helper 자체는 바꾸지 않았고 직접 호출은 양쪽 모두
0.7~0.8초 수준이었다. 소스의 불필요한 대기와 큰 supervisor 차이, 수정 후
네이티브/앱 양쪽의 감소가 해당 수신 대기가 주된 병목이었다는 근거다.

앱 정렬은 이미 첫 페이지가 있는 상태에서 시작한다. 따라서 8페이지 전체
수신과 같은 지표가 아니다. 네이티브 측정에는 XAML·모델 append가 없으며,
앱에는 모델/화면 반영과 UIA 관찰 비용이 포함된다. 별도 실행의 차이를
빼서 모델 또는 최종 픽셀 시간으로 확정하지 않는다.

200개 사전 확인의 시작 관찰은 1,385.265→3,969.704ms, 정렬은
316.073→351.122ms였다. 빌드 직후 첫 실행의 편차도 보존하며, 모든 시작
시간이 개선됐다고 주장하지 않는다. 메모리는 앱 본체의 50ms 표본 RSS다.

## 검증과 정리

- 관련 소스 계약 **20/20 PASS**: 수신 진행 시 즉시 반복, 취소/시간/프레임
  검사 순서, 종료 후 잔여 응답과 기존 broken-pipe 재시도 보호.
- 새 네이티브 fixture는 실제 제품 supervisor를 MSVC 18.x의 `/O2 /MD`
  조건으로 직접 빌드한다. `shell_navigation_core.cpp`, `shell_enum_bridge.cpp`
  및 supervisor를 링크하며 XAML은 포함하지 않는다. 200/8,000개, 페이지
  개수·오프셋·중복 없는 전체 이름·성공 응답·폴더 PIDL을 실제 검사했다.
- 실제 앱 전후 모두 정렬 최종 행, 스크롤, 진행 중 새 탐색과 늦은 결과
  거부, 종료 0, 기존 설정 존재/해시 및 소유 파일 바이트 보존 **PASS**.
- canonical `fly.bat build Release` 종료 0. 기존 산출물은 유지했으나
  LTCG가 IPDB/IOBJ 불일치로 25,321개 함수 전체 컴파일에 폴백했다.
- 성공 후 native fixture/프로필/실행 파일·obj와 앱 임시 fixture/프로필을
  제거했다. 작은 측정/컴파일 기록은 남기고 기존 호환 앱 런타임은 유지했다.
- 제품 화면 구성을 바꾸지 않았다. 별도 픽셀·전체 GUI·기존 입력 응답성
  반복·제외된 G03~G05 및 중단된 G07은 실행하지 않았다.

# Phase 5 follow-up: real WinUI 3 controls to existing flyExplorer command routing

Date: 2026-09-28. Production main and existing binary remain unchanged; production executable revision 6d1f76388b0b8326568478ce35814aba1eb69a0e. **Experiment-only** source: [phase5 experimental branch](https://github.com/tngkrwlsmd/flyExplorer/tree/experiments/phase5-real-winui3-20260928/experiments/phase5_winui3), commit e845eb45f3bd3cf978bbecaecf7984dc6f0d22a0. No actual WinUI replacement was merged into the product.

## Actual evidence

1. In source, src/fxfile/cmd/router/cmd_command_map.cpp binds ID_GO_BACK, ID_GO_FORWARD and ID_GO_UP to existing GoDirect*Command objects. src/fxfile/main_frame.cpp routes native commands through MainFrame::OnCmdMsg -> executeCommand -> CommandContext. src/fxfile/cmd/cmd_history.cpp and cmd_go_path.cpp delegate the respective actions to actual ExplorerCtrl. These are code-path observations, not evidence that the existing engine was separately linked into WinUI 3.
2. With a synthetic folder and **private copied six-file** current user UI profile, an isolated, test-owned real fxfile.exe was launched. Global hotkey/tray/startup, shell context registration and single-process routing were disabled only in the copied profile and separate APPDATA. Native scalar, timeout-protected WM_COMMAND (32004 Up, 32006 Back, 32007 Forward) on the **real MainFrame**, not the separate dark scrollbar overlay HWNDs, returned a handled message and changed the real product title My Music -> My Documents -> My Music -> My Documents. Test product exit 0; SHA256 of all original six UI files unchanged. Full HKCU and complete user-profile isolation were not verified.
3. Added an explicit **test-only cross-process bridge** in the actual WinUI 3 navigation PoC. Both test-owned product PID and MainFrame HWND must be supplied in flags. The bridge checks owning PID, application basename, window title and an allowlist of three native command IDs imported from the actual product resource.h. SendMessageTimeoutW dispatches only scalar WM_COMMAND, no cross-process user pointers. No automatic discovery of existing user instances.
4. The checked-in test_real_product_bridge.py starts and owns **both** isolated processes, finds the actual native product main window, clicks the real WinUI 3 Up/Back/Forward XAML buttons via UI Automation, verifies each resulting **real product** main-window title and reflected WinUI title/status, checks normal exit 0 of both and checks original six user-file hashes. All three connected GUI command steps passed at actual 96 DPI. The independent WinUI 3 navigation test_gui.py also passed its own Up/Back/Forward, Enter, invalid path, Escape, resize and hover GUI regression at 96 DPI; WinUI x64 build and project source invariants passed. Private test artifacts stay ignored and local.
5. An earlier diagnostic mistakenly targeted a top-level flyExplorer dark scrollbar overlay instead of MainFrame, which yielded no navigation evidence; filtering the process's real titled MainFrame corrected the test. The genuine observed product-command results were obtained only after selecting the appropriate main HWND. This was test targeting, not a confirmed product defect.

## What the proof does not establish

The experiment has **two separate processes**. WinUI 3 has not been hosted in the existing MFC process, and product C++ ExplorerCtrl has not been directly linked into the WinUI 3 application. The synthetic standalone NavigationModel is used only for independent standalone mode and must not be mistaken for actual engine reuse.

The test bridge's path field is intentionally read-only and displays the product window title, not the full active filesystem/Shell path. Active-pane command enabled-state parity, address input forwarding, cross-thread callbacks, Shell non-filesystem folders, multi-panel/tab focus, production installer/rollback and long-term performance/maintenance cost **remain untested**. Real 125/150/200% DPI and actual operating-system High Contrast also remain NOT TESTED; no user's global screen/accessibility settings were changed.

## Build compatibility and cost evidence

The real Visual Studio 2026 C++/WinUI3 project is configured from the installed official template; pinned Microsoft.WindowsAppSDK 2.5.1 and supporting official packages are restored to a private worktree-local NuGet cache. The actual XAML/C++ project compiles, launches and passes the above UI tests without installing a new machine-wide workload. **Earlier observation, superseded by the later build fix below:** VS18's ordinary ResolveNuGetPackageAssets target requests UAP,Version=v10.0 but native C++ NuGet restore produces native,Version=v0.0. Setting a singular TargetFramework, passing native TargetFrameworks and testing an altered ApplicationType did not yield a supported clean build. The experimental build currently succeeds only after restoring official packages and setting ResolveNuGetPackages=false during compilation, using generated package imports. This is a PROTOTYPE-ONLY workaround and is not acceptable as validated production packaging. The upstream NuGet C++ target-framework support issue at https://github.com/NuGet/Home/issues/11009 is related background, not proof of the local error's precise cause.

Neither the cost of shipping this interprocess test bridge nor the mature MFC app can be compared fairly to an incomplete single-surface WinUI PoC. Avoid invented lifecycle savings, memory figures or a full migration verdict.

## Next bounded decision gates

1. On the **isolated** experiment branch, resolve NuGet target selection with a tested supported C++/WinUI3 unpackaged template or documented, verified asset handling. Do not promote the temporary workaround as a production fix.
2. Design and implement a same-process or otherwise supported product-facing navigation adapter on the owning UI thread: actual current-pane command state, full active address and path input validation, Back/Forward/Up, native Shell namespace and focus. Prevent command execution against the wrong pane and verify saved user layout copies, drag/drop and history.
3. Verify real 125/150/200 DPI and OS High Contrast in an independent account/VM, plus same-folder side-by-side Windows 11 Explorer visuals, keyboard/IME/accessibility, runtime/installer/rollback costs and measurable responsiveness.
4. Only with equivalent **production-relevant** feature and cost evidence consider incremental MFC work, a limited hybrid host or staged UI replacement. **No framework transition is approved or supported by this limited proof.**

No product source, executable or original six UI configuration files were changed. No system registry configuration changes were intentionally performed, but comprehensive HKCU preservation was not independently verified. No GitHub Actions workflows were dispatched.


## Later 2026-09-28 verification: normal NuGet asset resolution and remaining bridge teardown defect

On the connected VS2026 Windows development PC, the isolated WinUI 3 C++ PackageReference restore graph selected native,Version=v0.0. MSBuild otherwise tried UAP,Version=v10.0 and an unrelated win10-x64 NuGet runtime ID. The experimental build script now explicitly selects the actual native NuGet moniker (with escaped comma for CMD), clears the UAP fallback and NuGet runtime identifier, and restores pinned official packages into ignored local cache. Normal ResolveNuGetPackageAssets and full Debug|x64 XAML/C++ linking both PASSED without the former ResolveNuGetPackages=false bypass. The earlier ad hoc TargetFramework=uap10.0 was removed. Reproducibility on a fresh machine, Release builds and product packaging remain NOT TESTED.

After that build, the independent actual 96-DPI WinUI 3 mouse/keyboard navigation GUI PASSED with clean process exit. Follow-up cross-process testing exposed intermittent shared-desktop pointer automation: a Back click sometimes failed to fire any button event, as confirmed by per-command WinUI status remaining at the preceding Up ID. Switching only the test to UI Automation InvokePattern delivered all real Up/Back/Forward commands and actual product title changes, preserving six original user settings SHA256 hashes. However the owned WinUI 3 helper subsequently sometimes failed to shut down before the 8-second close timeout, including after releasing UIA wrappers. The strict bridge regression is therefore FAIL, not a fully green test. This test-only bridge is not product integration; the original product code and binary were not modified.

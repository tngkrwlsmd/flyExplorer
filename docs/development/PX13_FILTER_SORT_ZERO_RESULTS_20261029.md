## 실제 앱 표시 관측과 메모리

같은 소유 폴더를 이전 runtime, 후보 runtime 순서로 열었다. 왼쪽 전체 모델 8,000개 준비 후 각 이름 정렬 모드에서 필터 해제→80개 필터 적용을 3회 수행했다. 측정 경계는 UI 자동화의 값 입력 시작→항목 수 80 및 예상 첫 행을 관측한 시점이다. 자동화 호출·폴링·행 조회 비용이 포함되며 최종 픽셀 표시 시간이나 순수 제품 CPU 시간이 아니다. 필터 후 스크롤하며 80개 이름 전체의 순서를 두 모드에서 확인했다.

RSS는 각 모드 종료 시 전체 앱의 한 시점 작업 메모리다. 오른쪽 패널은 초기 제한 페이지 상태이며, 두 패널 전체 모델·최고 메모리·장기 누수 검증이 아니다. 캐시/부하를 통제한 무작위 교차 앱 시험도 아니다. [원래 표본과 결과](PX13_FILTER_SORT_MEASUREMENTS_20261029.json)를 보존한다.

소스상 필터 변경은 해당 패널의 목록을 다시 만들고 선택/항목 수를 갱신한다. 정렬 비용은 수 ms, 앱 관측은 약 1초로 다른 비용이 훨씬 크다. 따라서 이 자료만으로 느려진 제품 구간을 특정하거나 전체 앱 회귀가 없다고 단정할 수 없다. 이 변경의 순서 정확성과 연산 감소는 확인됐으나 **앱 체감 개선·무회귀 판정은 미확인**이다. 새 제품 병목의 근거 없이 목록/Controller를 다시 쓰거나 성공한 기존 PX13 시험을 늘리지 않는다. 20,000/25,000 상한도 유지한다.

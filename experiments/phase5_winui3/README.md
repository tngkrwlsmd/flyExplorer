# Phase 5 strict bridge teardown: test harness defect corrected (2026-09-28)

**Observed root cause, not a WinUI/product shutdown defect:** The strict bridge test's finalizer previously rediscovered a test-owned process window using `top_for(pid, lambda title: bool(title))`, which returns zero unless EXACTLY ONE visible titled window exists. On the connected Windows 11 PC, the WinUI 3 process has both its actual main window and a separate visible notification-host window. During a failing baseline test, all three real commands passed, both windows remained visible and responsive, and NO WM_CLOSE was posted to the WinUI main HWND; the harness then timed out and force-terminated it.

**Minimal correction:** Keep the actual product MainFrame `ph` and WinUI main `wh` HWNDs previously established under their explicitly owned process IDs. During finalization select exactly those handles, verify each HWND still belongs to the expected owned PID, and post WM_CLOSE only to that matching HWND. No production, XAML or application shutdown code was changed. The hypothesis that UIA COM wrapper lifetime caused the failure was also tested with a short-lived UIA subprocess and **did not** fix the timeout; that diagnostic workaround was removed.

**Actual regression:** Original baseline strict bridge FAIL reproduced with all Up/Back/Forward commands succeeding and WinUI forced termination. After the minimal fix, the strict bridge passed once and then passed **three more consecutive** complete real 96-DPI cross-process runs: all three actual product commands and WinUI status/title reflections, exit code zero of both owned processes, and original six user configuration file SHA256 hashes unchanged on every run. The separate real WinUI 3 pointer/keyboard GUI test passed with exit code zero. Python test syntax and git diff checks passed. These checks used the existing experimentally built binary; no fresh C++ rebuild was necessary because only the Python test harness changed. The additional visible notification-host window was observed on this PC; other Windows environments remain untested.

**Limitations remain:** This proves reliable teardown for the observed test-harness scenario, not same-process integration, complete HKCU isolation, full active-pane/address/Shell parity, real higher DPI/OS High Contrast, clean-machine WinUI build, or product packaging. GitHub Actions were not run; existing product source/executable and original user settings were not modified.
